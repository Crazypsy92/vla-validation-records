# VLA 项目需求拆解与个人工作路线

> \[!abstract\] 文档定位
> 本文档是针对当前工业智能作业项目的**项目需求分析、系统链路梳理和个人工作开展路线**，不是通用的
> AI 模型学习教程。
>
> 项目整体涉及 3D 视觉反馈与自适应跟踪控制、轻量化 VLA
> 多模态决策、语义驱动动作生成与异构设备统一控制。个人主要负责其中的
> **VLA 多模态决策模型相关工作**，需要先补齐 LLM、VLM
> 等前置知识，再逐步完成 VLA
> 选型、推理复现、场景适配、知识增强、模型优化和部署验证。
>
> **最终目标：**
> 形成一个能够理解任务、利用视觉和设备状态进行决策、输出规范动作语义或模型动作序列，并能与下游控制系统协作的轻量化
> VLA 方案。

> \[!warning\] 范围声明
> 项目书描述的是整体项目，不代表个人需要独立完成所有模块。本文明确区分：
> **项目整体工作：** 从现场感知、VLA 决策到设备执行与反馈的完整系统链路；
> **个人负责工作：** VLA 多模态模型及其输入输出、推理复现、场景适配和上下游接口；
> **前置学习工作：** 为完成 VLA 工作必须补齐的模型与工程知识。
>
> 机械臂或其他设备的底层控制可以由独立控制模块承担，不要求在当前模型验证阶段重新开发或接入。具体设备、产线工位、传感器、NPU
> 型号和数据集仍需项目组确认；现有机械臂控制能力可作为后续下游执行端进行接口适配。

## 0 项目正式定义与当前阶段边界

### 0.1 项目正式定义

**本项目定位为：面向工业智能作业场景的轻量化 VLA 多模态决策模型研究与系统接入。**

总体上按照 VLA 技术路线开展：模型接收视觉观测、自然语言任务指令以及模型所需的设备/机器人状态，完成场景理解与任务决策，并输出与所采用模型相匹配的动作结果。动作结果可以是高层动作语义、动作原语，也可以是模型直接预测的连续动作或 Action Chunk；具体形式由模型架构和下游接口决定。

完整系统的目标链路为：

```text
视觉观测 / 场景信息 + 任务指令 + 必要的设备状态
                    ↓
              轻量化 VLA 模型
                    ↓
       任务决策 / 动作语义 / 动作序列
                    ↓
       独立的动作校验与控制接口模块
                    ↓
          机械臂或其他设备执行
                    ↓
          执行状态与新观测反馈
                    └──────────→ 下一轮决策
```

个人工作重点是 VLA 模型本身及其上下游数据接口，包括模型架构学习、预训练模型选型与推理复现、输入输出分析、场景适配、必要的知识增强、模型优化和后续部署。已有的机械臂控制模块保持独立，后续通过约定接口接收模型输出；不要求为了验证模型而重写底层控制。

**术语边界：** 使用 VLM/LLM 根据视觉描述生成高层任务 JSON，可以作为模块化系统中的语义决策部分，但单独看并不等于模型已经具备 VLA 动作策略。像 SmolVLA 这类模型，如果实际接收其规定的多模态观测和状态并由模型前向推理生成动作块，则属于 VLA 模型推理验证。项目总体按 VLA 方向推进，但每个基线模型的能力必须按其真实输入输出准确描述。

### 0.2 当前阶段正式定义：只验证模型能否成功推理

当前阶段限定为**预训练模型的独立推理可用性验证**。核心问题只有一个：模型能否在当前实验环境中正常加载，接收符合模型要求的输入，完成真实前向推理，并产生有效、可解析的模型输出。

当前阶段的验收条件：

1. 模型及其依赖能够正常加载，权重与配置匹配。
2. 能够按照模型要求准备输入，例如图像/视觉观测、任务指令，以及该模型要求的机器人状态；不强制所有模型使用完全相同的输入字段。
3. 确认执行的是实际模型推理，而不是模拟输出、硬编码结果或仅调用接口但未运行模型。
4. 推理能够正常结束，并生成模型规定格式的输出，例如动作张量或 Action Chunk。
5. 输出的数据结构、维度、数据类型及数值有效性能够检查，结果可以保存并复现。

**当前阶段通过标准：** 上述推理链路成功，即判定该模型在当前环境下“能够运行并完成推理”。当前不要求模型输出已经能够驱动指定机械臂，也不要求动作在真实设备上执行成功。

### 0.3 当前阶段明确暂缓的内容

- 机械臂实体运动、夹爪控制和真实抓取。
- 将模型动作输出映射为指定机械臂的关节/末端控制指令。
- 仿真或真机中的动作执行成功率、抓取成功率和完整闭环任务成功率。
- 控制接口联调、设备协议适配和执行反馈闭环。
- 为满足实时性而进行的推理加速、量化、剪枝、蒸馏或 NPU 部署。

这些工作属于后续系统适配、优化和联调阶段，不是当前模型推理验证的前置条件。

### 0.4 当前阶段的时间与性能原则

**当前不设置推理时间、吞吐率或实时性门槛。** 模型推理耗时可以记录，作为了解模型资源需求和后续优化的参考数据，但不能因为推理速度慢而判定本阶段失败。当前也不以项目书中的端到端延迟、规划频率或底层控制频率作为模型基线的通过条件。

当前只关注：模型是否成功加载、是否真正完成推理、是否生成有效输出。待模型能力和项目场景适配得到验证后，再根据目标硬件和系统需求决定是否开展性能优化。

### 0.5 当前验收与项目最终目标的关系

当前完成的是 VLA 模型侧的可运行性验证，不代表已经证明动作策略适用于真实设备，也不代表完整 VLA 系统已经完成。项目总体仍保留“感知—VLA 决策—控制接口—设备执行—状态反馈”的完整方向；只是将模型验证与机械臂执行解耦，先确认模型本身能够工作，再逐步推进接口适配和系统联调。

## 1 项目背景与总体目标

### 1.1 项目场景

根据项目书，项目面向锂电产线的智能化、柔性化和无人化需求，重点关注以下典型作业场景：

  ----------------------------------------------------------------------------------------------------------------------------------------
  场景                    主要问题                                            项目希望实现的能力
  ----------------------- --------------------------------------------------- ------------------------------------------------------------
  高速移动抓取            目标位置持续变化，视觉反馈与控制响应存在滞后        通过 3D 视觉反馈和自适应控制，提高动态跟踪与作业能力

  具身智检                复杂视觉环境下的缺陷识别、判断和处理                利用多模态 AI 理解现场信息，辅助检测、判断和任务决策

  多异构设备协同          AGV、机器人及其他设备接口不同，任务调度和协作困难   将高层任务语义转换为设备可执行的动作，并实现统一接入与协同
  ----------------------------------------------------------------------------------------------------------------------------------------

项目不是单纯训练一个 VLA
模型，而是希望形成从现场感知到智能决策，再到设备执行和反馈的完整链路。该完整链路是项目总体目标，不代表当前模型推理验证阶段必须完成设备执行与反馈。

### 1.2 项目总体技术目标

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  编号              技术方向                         核心目标                                                     主要技术
  ----------------- -------------------------------- ------------------------------------------------------------ --------------------------------------------------------------
  A                 基于 3D 视觉反馈的自适应跟踪控制 解决视觉观测频率与设备控制频率不匹配、动态跟踪滞后等问题     3D 视觉、位姿估计、EKF、运动学模型、视觉伺服

  B                 面向锂电产线的轻量化 VLA         让模型融合视觉、语言和设备状态，理解任务并生成决策           LLM、VLM、VLA、RAG、量化、剪枝、蒸馏、NPU
                    多模态决策模型                                                                                

  C                 语义驱动动作生成与统一控制接口   将高层任务语义转成设备可执行的动作，实现异构设备接入与协作   动作原语、语义转译网关、Modbus、Profinet、EtherCAT、任务协调
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

### 1.3 项目最终要形成的能力

1.  现场信息能够被采集、处理并形成可供决策使用的状态。
2.  VLA 能够结合任务指令、视觉信息及相关状态进行多模态决策。
3.  工业知识能够按需提供给决策过程，减少不符合工艺约束的输出。
4.  模型输出能够转换为标准化动作语义，而不是直接输出未经约束的底层控制信号。
5.  下游控制系统能够把动作语义映射到具体设备接口。
6.  执行结果和设备状态能够反馈给上层，支持任务继续、停止或重新规划。
7.  模型能够在目标边缘计算平台上运行，并满足项目确认后的资源、延迟和可靠性要求。

以上是项目整体能力目标。当前阶段仅验收模型独立推理是否成功，设备执行、闭环效果和边缘部署均按后续阶段推进。

> 模型单体指标。

### 2.3 VLA 模块的输入与输出需求

VLA
的具体输入输出必须结合最终设备和所选模型定义。当前先建立候选接口框架。

  -------------------------------------------------------------------------------------------------------------
  类型                    候选数据                                         需要确认的内容
  ----------------------- ------------------------------------------------ ------------------------------------
  视觉输入                RGB 图像、视频帧、视觉特征、可选深度信息         分辨率、视角、帧率、预处理

  语言输入                任务指令、任务目标、操作约束                     指令模板、语言范围、任务表达规范

  状态输入                设备位置、速度、运行模式、任务状态、传感器状态   状态字段、单位、更新频率、数据来源

  知识输入                工艺规则、设备能力、作业约束、异常处理规则       知识库格式、检索方式、版本管理

  模型输出                任务决策、动作类别、动作参数、动作块或策略输出   输出形式由模型架构决定

  执行反馈                成功、失败、执行中、超时、异常码、新状态         反馈接口和状态定义
  -------------------------------------------------------------------------------------------------------------

**关键边界：** VLA
输出不一定直接等于电机控制量。项目初期应优先定义模型输出的高层动作语义或设备相关动作表示，再由下游控制接口完成参数映射、范围检查和执行。

## 3 项目整体技术链路

### 3.1 全链路概览

下图表示项目最终系统链路。当前模型验证只覆盖“VLA 输入组织 → VLA 推理 → 模型输出”部分，后续动作校验、设备适配、机械臂执行和反馈闭环暂缓。

``` mermaid
flowchart TD
    A["现场设备与作业对象"] --> B["多源信息采集"]
    B --> C["3D视觉感知 / 设备状态采集"]
    C --> D["状态估计与信息融合"]
    D --> E["VLA 输入组织"]
    F["任务指令"] --> E
    G["工业知识库"] --> H["知识检索 / 约束增强"]
    H --> E
    E --> I["轻量化 VLA 多模态决策"]
    I --> J["结构化任务 / 动作语义"]
    J --> K["动作校验与语义转译网关"]
    K --> L["设备能力与协议适配"]
    L --> M["AGV / 机器人 / 其他设备控制器"]
    M --> N["设备执行"]
    N --> O["执行状态与传感器反馈"]
    O --> C
    O --> P["任务状态更新 / 异常处理"]
    P --> E
```

### 3.2 三个技术方向之间的关系

#### A：3D 视觉反馈与自适应跟踪控制

**主要职责：**
提供可靠、及时的视觉观测和设备状态反馈，解决动态场景下的位姿估计、跟踪和底层控制问题。

项目书提出的技术思路：

1.  通过 3D 视觉传感器获取目标局部点云或视觉信息。
2.  将视觉解算位姿作为观测信息。
3.  将运动学模型等作为状态演化信息。
4.  使用 EKF 等方法融合不同频率的信息。
5.  为底层控制提供更连续的状态估计和反馈。

**与 VLA 的接口：**

-   提供模型需要的视觉观察或经过处理的状态。
-   提供目标状态、设备状态和必要的置信度信息。
-   提供更新后的状态，供下一轮决策使用。

**个人工作边界：**
需要理解输入数据、坐标、频率、状态字段和误差含义；不默认负责 EKF
算法、视觉伺服控制器或机器人底层运动控制的完整研发。

#### B：轻量化 VLA 多模态决策模型

**主要职责：**
将任务语言、视觉观察、设备状态和相关知识结合起来，完成任务理解与高层动作决策。

核心工作：

1.  LLM 基础与模型推理能力。
2.  VLM 视觉语言理解。
3.  VLA 架构和动作生成机制。
4.  工业知识检索与决策增强。
5.  模型选型、预训练权重推理和场景适配。
6.  根据数据和效果判断是否需要微调。
7.  模型量化、压缩、推理优化和边缘部署。
8.  输出稳定、可校验、可追踪的动作语义或模型结果。

**这是个人主要负责的技术方向。**

#### C：语义驱动动作生成与统一控制接口

**主要职责：** 将 VLA 的高层决策转换为具体设备可以理解和执行的指令。

核心工作：

1.  定义统一的动作语义和动作原语。
2.  建立动作参数、设备能力和执行条件的映射。
3.  设计指令转译网关。
4.  接入 Modbus、Profinet、EtherCAT 等设备协议。
5.  实现异构设备任务协调和执行反馈。

**与 VLA 的接口：**

-   VLA 提供结构化动作意图或任务决策。
-   C 模块负责动作合法性检查、设备适配和协议转译。
-   C 模块返回执行结果、异常状态和设备反馈。

**个人工作边界：** 需要参与动作语义、输出 Schema
和接口联调设计；不默认负责全部工业协议驱动、多机调度算法和设备控制器开发。

### 3.3 分层控制关系

``` mermaid
flowchart TB
    A["任务层：用户 / 工艺任务指令"] --> B["决策层：LLM / VLM / VLA / 知识增强"]
    B --> C["动作语义层：任务分解 / 动作原语 / 参数"]
    C --> D["协调层：状态机 / 任务调度 / 设备适配"]
    D --> E["控制层：机器人控制器 / AGV 控制器"]
    E --> F["执行层：电机 / 机构 / 传感器"]
    F --> G["反馈层：状态 / 结果 / 异常"]
    G --> B
```

> \[!important\] 控制频率与模型决策频率需要分层 项目书提出全局规划
> 1～5Hz、实时控制
> 30～50Hz，并提及毫秒级伺服响应。系统设计应明确：VLA/高层决策负责任务级或较低频的决策；设备控制器负责确定性较强的高频控制；反馈和异常事件可以触发重新决策。
>
> 不应默认每个 30～50Hz 控制周期都同步等待一次 LLM/VLA 完整推理。

## 5 VLA 工作包的具体需求

### 5.1 模型能力需求

  能力       具体要求                                   验证方式
  ---------- ------------------------------------------ --------------------
  指令理解   理解作业目标、对象、约束和完成条件         固定任务指令测试集
  视觉理解   利用现场图像识别与任务相关的场景信息       图像/视频样例测试
  状态理解   结合设备状态判断当前是否适合执行           状态输入对照测试
  知识增强   检索相关工艺、设备和安全约束               有/无知识增强对比
  动作决策   生成与任务相符的动作或动作语义             动作结果与标注对比
  异常处理   对信息不足、冲突或异常状态采取保守策略     异常场景测试
  输出规范   输出可解析、字段完整、参数合法的结果       Schema 自动校验
  可追踪性   记录输入、模型版本、输出、检索和执行结果   日志与实验记录

### 5.2 建议的模型输出分层

不要在项目初期直接要求模型输出设备底层寄存器、总线报文或电机
PWM。先定义中间层输出。

以下仅为接口讨论模板，实际字段需要与 C 模块共同确定：

``` json
{
  "task_id": "task_0001",
  "decision": "execute",
  "task_intent": "move_material",
  "target": {
    "object_id": "target_01"
  },
  "action_sequence": [
    {
      "primitive": "approach",
      "parameters": {
        "target_id": "target_01"
      }
    },
    {
      "primitive": "transfer",
      "parameters": {
        "destination": "station_A"
      }
    }
  ],
  "constraints": {
    "requires_validation": true
  },
  "confidence": 0.92,
  "reason": "符合当前任务与设备约束"
}
```

该示例不是已经确定的项目协议。`confidence`
也不能直接当成模型真实可靠性证明，必须通过独立测试校准。

### 5.3 异常与安全要求

至少考虑以下情况：

-   输入图像缺失、模糊或过期。
-   目标状态与设备状态不一致。
-   知识库没有检索到相关约束。
-   模型输出字段缺失或格式错误。
-   动作参数超出设备能力。
-   设备处于忙碌、故障或急停状态。
-   指令相互冲突或超出授权范围。
-   执行超时、执行失败或反馈丢失。

处理原则：

1.  模型只提供决策候选，不直接绕过控制系统执行。
2.  动作 Schema 必须经过程序校验。
3.  设备能力、速度范围、区域限制由可信配置和控制系统管理。
4.  不确定或异常时，允许拒绝执行、暂停或请求人工确认。
5.  急停、限位和安全联锁由独立控制系统保障。

## 8 数据、模型与训练策略

### 8.1 模型使用顺序

  顺序   工作方式                      目的
  ------ ----------------------------- ------------------------
  1      使用预训练模型推理            建立能力基线
  2      调整输入、Prompt 和输出约束   解决低成本适配问题

  4      调整动作映射和程序工作流      解决系统接口问题
  5      小规模微调或模仿学习          解决明确的模型能力缺口
  6      量化、剪枝、蒸馏              满足资源约束
  7      目标 NPU 部署                 验证边缘运行能力

### 8.2 什么时候需要训练或微调

不要把"项目使用 VLA"直接等同于"必须训练一个 VLA"。

  -------------------------------------------------------------------------------------
  问题现象                       优先排查                       是否立即训练
  ------------------------------ ------------------------------ -----------------------
  模型理解错指令                 指令定义、Prompt、模型能力     否

  模型看不清场景                 图像质量、预处理、视觉能力     否

  模型输出字段不稳定             Schema、解码约束、后处理       否

  动作参数不符合设备要求         动作映射、设备能力配置         否

  知识回答不符合工艺要求         知识库质量、检索和约束注入     否

  对特定设备动作策略持续不适应   数据覆盖、动作空间、策略能力   评估微调

  新场景泛化明显不足             训练数据和模型泛化能力         评估数据采集与微调
  -------------------------------------------------------------------------------------

### 8.3 数据准备原则

VLA 的数据不只是图片和文字，通常还需要动作或轨迹信息。

需要确认：

-   视觉观察与动作是否时间对齐。
-   设备状态是否有统一单位和坐标定义。
-   动作是否经过归一化，如何还原。
-   不同设备的动作空间是否一致。
-   是否记录任务成功、失败和异常。
-   数据是否覆盖不同工况、环境和设备状态。
-   训练、验证、测试数据是否避免泄漏。
-   数据是否具备授权和使用条件。

## 9 轻量化与端侧部署路线

### 9.1 先测量，再优化

1.  在开发电脑上运行未优化模型。
2.  记录任务效果、延迟、内存和显存。
3.  确认模型是否真的超过目标设备预算。
4.  先尝试推理框架和精度优化。
5.  再尝试量化。
6.  如果仍不满足，再评估剪枝或蒸馏。
7.  最后在目标 NPU 上验证实际效果。

### 9.2 优化方式对比

  方法            主要目的                     主要风险
  --------------- ---------------------------- ----------------------
  FP16 / BF16     降低权重和计算开销           硬件支持差异
  INT8 / INT4     降低模型存储和计算成本       精度下降、算子限制
  结构化剪枝      减少部分网络结构             需要结构和工具支持
  知识蒸馏        用较小模型学习较大模型能力   需要数据和训练成本
  KV Cache 优化   降低自回归推理重复计算       内存策略与上下文限制
  推理引擎优化    提高执行效率                 算子兼容和部署复杂度

### 9.3 端侧部署验收内容

  类别     指标
  -------- ----------------------------------------
  模型     参数量、权重文件大小、模型精度
  资源     峰值内存、NPU/GPU 使用率、带宽
  延迟     预处理、模型推理、后处理、端到端延迟
  效果     任务成功率、动作输出正确率、异常拒绝率
  功耗     平均功耗、峰值功耗、温度
  稳定性   连续运行时间、异常恢复、内存泄漏
  兼容性   算子覆盖、模型转换成功率、版本依赖

## 10 项目测试与验收指标

### 10.1 当前阶段：模型推理可用性验收

当前阶段只回答“模型能不能成功推理”，不评价它能否控制真实机器人完成任务。

| 验收项 | 检查内容 | 当前通过条件 |
|---|---|---|
| 模型加载 | 权重、配置、Tokenizer/处理器及依赖 | 模型正常加载，无阻断性错误 |
| 输入准备 | 按模型要求准备图像/视觉观测、任务指令和必要状态 | 输入字段、尺寸、类型符合模型接口 |
| 真实推理 | 确认实际执行模型前向推理 | 推理正常结束，不是模拟或硬编码输出 |
| 输出生成 | 获取模型规定的输出，如动作张量或 Action Chunk | 输出存在，且结构符合模型定义 |
| 输出有效性 | 检查形状、维度、数据类型及 NaN/Inf 等异常值 | 输出可解析，基础数值检查通过 |
| 结果留存 | 保存输入配置、模型版本、运行日志和输出样例 | 能够复现本次推理过程 |

**当前阶段 PASS 定义：** 模型成功加载，使用符合要求的输入完成真实推理，并生成结构有效、可检查和可保存的输出，即判定推理验证通过。

当前不要求：动作在仿真或真机中执行成功、抓取成功、机械臂运动正确、完整闭环任务成功，也不要求达到指定推理延迟、吞吐率或实时控制频率。

### 10.2 当前阶段记录项（不作为通过门槛）

以下数据可以随测试记录，主要用于了解模型和运行环境，不作为当前阶段的 PASS/FAIL 条件：

-   模型名称、版本、权重来源、参数量和文件大小。
-   操作系统、Python/PyTorch/Transformers 版本及推理设备（CPU/GPU）。
-   输入图像数量、分辨率、指令内容及状态字段。
-   模型加载是否成功、推理是否成功、输出张量形状和数据类型。
-   单次推理耗时、峰值内存/显存占用等资源数据。
-   错误日志、异常原因和复现步骤。

**时间原则：** 当前没有推理耗时上限。即使一次推理需要几十秒，只要模型真实完成推理并生成有效输出，仍然可以通过当前阶段验收。记录耗时是为了后续有依据地决定是否优化，而不是现在就追求速度。

### 10.3 后续阶段：模型能力与系统指标

当工作从“模型能否运行”进入“模型是否适合项目任务”后，再逐步评估以下指标：

| 指标层级 | 指标 | 说明 |
|---|---|---|
| 输入层 | 输入完整率、数据时效性 | 模型收到的数据是否完整且足够新 |
| 理解层 | 指令理解准确率 | 是否正确理解任务目标和约束 |
| 视觉层 | 视觉状态判断准确率 | 是否正确理解任务相关场景 |
| 知识层 | 检索命中率、知识约束遵循率 | 是否找到并使用相关知识 |
| 决策层 | 任务决策正确率 | 决策是否符合任务规则 |
| 动作层 | 动作输出有效率、动作映射正确率 | 输出动作是否符合模型定义并能正确映射 |
| 安全层 | 非法动作拦截率、危险动作漏检数 | 不合法输出是否被阻止 |
| 系统层 | 端到端延迟、任务成功率 | 完整系统是否满足要求 |
| 部署层 | 内存、功耗、稳定性 | 目标设备能否持续运行 |

### 10.4 后续阶段建议测试矩阵

| 测试类别 | 测试内容 | 目的 |
|---|---|---|
| 正常场景 | 标准任务、正常状态、清晰视觉输入 | 建立基线 |
| 视觉变化 | 光照变化、遮挡、视角变化 | 测试视觉鲁棒性 |
| 状态变化 | 设备忙碌、位置变化、状态延迟 | 测试状态理解 |
| 指令变化 | 同义表达、缺失参数、模糊指令 | 测试语义理解 |
| 知识变化 | 有知识、无知识、冲突知识 | 测试知识增强 |
| 异常场景 | 设备故障、反馈超时、目标不存在 | 测试异常处理 |
| 输出异常 | JSON 错误、未知动作、越界参数 | 测试程序校验 |
| 资源压力 | 内存不足、推理变慢、长时间运行 | 测试部署稳定性 |

### 10.5 对项目书指标的拆分建议

| 项目书指标 | 建议拆分方式 | 需要确认 |
|---|---|---|
| 模型规模 0.5B～3B | 比较不同模型规模下的效果与资源 | 参数量统计口径 |
| 指令转译准确率 ≥99% | 单独评估结构化动作映射正确率 | 样本量、标签和判定规则 |
| 端到端延迟 ≤10ms | 拆分模型、网关、通信和控制链路 | 起止点及统计方式 |
| 全局规划 1～5Hz | 统计任务决策刷新周期 | 是否要求每次模型推理 |
| 实时控制 30～50Hz | 统计底层控制周期和抖动 | 控制器和执行端责任 |
| 毫秒级伺服 | 统计伺服响应与跟踪误差 | 主要由控制模块验证 |

> \[!warning\] 不要提前承诺指标
> 需要先明确模型架构、目标硬件、输入长度、输出长度、动作表示和测试口径，再判断指标是否可实现。对于无法由
> VLA 单模块负责的指标，应明确由系统集成或控制模块共同验收。以上项目书指标属于后续系统目标，不是当前模型推理验证的验收条件。

## 11 风险、难点与待确认事项

### 11.1 主要风险

  ---------------------------------------------------------------------------------------
  风险                    可能表现                         应对方式
  ----------------------- -------------------------------- ------------------------------
  项目场景不明确          模型不知道具体要完成什么任务     先确定首批任务和验收样例

  输入接口不统一          图像、状态、时间戳和坐标不匹配   建立统一数据 Schema

  动作空间不明确          模型输出无法对应设备动作         与 C 模块共同定义动作原语

  训练数据不足            VLA 无法适应实际设备             先做基线评估，再制定采集计划

  模型规模过大            当前硬件或 NPU 无法承载          先做资源预算和模型筛选

  NPU 算子不支持          模型转换失败或性能异常           提前做兼容性预检

  指标口径模糊            10ms、99% 无法客观验收           拆分指标并制定测试协议

  模型输出不安全          越界、冲突或无效动作             独立校验、权限控制和安全联锁

  系统责任边界不清        VLA 被要求承担底层控制任务       明确 A/B/C 模块接口和责任
  ---------------------------------------------------------------------------------------

**个人负责：**

``` text
LLM 前置知识
    ↓
VLM 多模态理解
    ↓
VLA 架构与模型选型
    ↓
预训练模型推理复现
    ↓
项目场景与动作接口适配
    ↓
知识增强 / 数据准备 / 必要时微调
    ↓
量化与模型优化
    ↓
NPU 边缘部署
    ↓
与上下游模块联调
```

**工作原则：**

-   当前先把预训练模型真实跑通，确认能成功推理并生成有效输出；不以推理速度作为当前验收门槛。
-   先使用预训练权重，不以从零训练为目标。
-   先理解模型架构、输入输出和动作表示，再决定是否开展场景适配或微调。
-   当前只做模型侧推理验证；机械臂执行、控制接口联调和反馈闭环放在后续阶段。
-   完整系统中，模型负责理解和决策，动作网关负责转译与校验，底层控制器负责实时执行。
-   后续如开展性能优化，必须有原始基线、对照实验和可复现结果。

> \[!success\] 最终目标 不是单纯"学会一个 VLA
> 模型"，而是能够负责项目中的 VLA
> 技术工作：从前置模型知识、模型选型与复现，到场景适配、知识增强、轻量化部署，再到与上下游系统完成接口联调和测试验收。
